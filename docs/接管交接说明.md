### 3.9 compress 入参容错（对接 billion-context 的第一刀）

**问题**：`acp-kernel@0.0.101` 的 `COMPRESS_TOOL.input_schema` 把「行格式」标为 PREFERRED（`m00150–m00220 optional topic` + 摘要正文，一次可传多段），但同版本的 `parseCompressInput()` 只认扁平对象 `{startRef,endRef,summary}` 和 `{content:[{startId,endId,summary}]}`；所有字符串/数组形状都返回 0 段。真实会话里 4 次 `compress` 有 2 次报 `No valid ranges were parsed. Provide a startRef/endRef pair plus a summary (see the tool description).` —— 模型照着 schema 写就必错，成功率只有 50%。

| 文件 | 改动 |
|---|---|
| `src/services/acp/parseRanges.ts`（新增） | `normalizeCompressRanges(input)`：把 schema 广告的所有形状归一成 `{startRef,endRef,summary,topic?}`。支持 header 行文本（`/^\s*m(\d{3,7})\s*(?:[–—\-~～]\|\.\.\|到)\s*m(\d{3,7})\s*(.*)$/i`）、字符串数组、`{content}`/`{ranges}`/`{blocks}` 容器、`{startId,endId}`、`{startRef,endRef}`、`{range:"m1–m2", summary}`；ref 补零成 5 位，去重、丢空摘要 |
| `src/services/acp/tools.ts` | `CompressTool.call` 先 `normalizeCompressRanges(args)`，为空再回落内核的 `parseCompressInput(args)`，其余逻辑不变 |
| `src/services/acp/parseRanges.test.ts`（新增） | 8 例：单块、多块、字符串数组、`{content:[对象]}`、`{ranges}`/扁平/`{range}`、`– — - 到` 变体、去重去空、垃圾输入 |

**验证**：`bun test src/services/acp` → 32 pass / 0 fail；`bunx tsc` 过滤 `parseRanges.ts` 无错误；`bun run build:bundle:cclite` 成功。

**与 billion-context 的关系（调研结论）**：上游 `ranxianglei/billion-context` 是**代理层**方案（`bili` 启动器 / 原生插件 / `/bili/` 前缀，在客户端与 API 之间注入同名的 `compress`/`decompress`/`search_context`/`acp_status` 四工具并跑 `acp-kernel`）。cclite 已经把同一个 `acp-kernel@0.0.101`（npm `latest`）**嵌进进程内**，两条路线互斥（同时开会双压缩）。所以「有机融合」不是再套一层代理，而是把上游在代理层解决掉的工程问题在 cclite 内部补齐。已补齐：计数口径（3.8）、撞墙兜底（3.7）、工具入参容错（本节）。**仍缺三项**：① 折叠块持久化——ACP 状态只在内存，进程退出或 `--resume` 后折叠块全丢，长会话会退回到原始历史；② 硬闸——0.95 阈值只是提示，模型不调 `compress` 仍会撞墙，目前只靠 413 兜底；③ 缓存记账——`cache_read` 与压缩后前缀的关系未纳入决策。建议按 ①→②→③ 继续。

### 3.11 ACP 折叠状态持久化（2026-10-30）

问题：折叠块只活在进程内存里，`--resume` 或重启后 ACP 状态归零，历史原样重发——等于把之前折掉的 token 全部再付一次，服务端前缀缓存也一起冷掉。

改动（`src/services/acp/`）：

| 文件 | 内容 |
|---|---|
| `persist.ts`（新） | `AcpSnapshot` 信封（version/key/savedAt/state/contentStore）；`loadAcpSnapshot` / `saveAcpSnapshot`（原子写：tmp + rename）/ `deleteAcpSnapshot` / `isAcpSnapshotCompatible` |
| `session.ts` | `getAcpSession()` 记录 key；`hydrateAcpSession(key, rawIds)` 只在首次挂载时读盘，块覆盖的消息必须仍存在才恢复；`persistAcpSession()` 按 block 签名节流，避免每轮重写大 store；`resetAcpSession()` 删除快照 |
| `stage.ts` | 每次 stage 用首条消息 uuid 作 key 触发 hydrate，处理完调用 persist |
| `persist.test.ts`（新） | 6 例：往返、未知会话、兼容/不兼容、无块、hydrate 恢复 |

落盘位置：`<项目>/.cclite/acp/<首条消息 uuid>.json`（`CCLITE_ACP_STATE_DIR` 可覆盖；旧版 `~/.claude/acp/` 仍作只读回落，读到后照常恢复）。目录内自带 `.gitignore`（内容 `*`），不会污染项目自身的 git 状态。key 用首条消息 uuid 是因为 transcript 重放时 uuid 不变；快照里每个 active block 的 `effectiveMessageIds` 必须全部出现在本轮 replay 中，否则判定 transcript 已被改写、丢弃快照（安全回落）。

验证：`bun test src/services/acp` 38 pass / 0 fail；`bun cclite.js -p "Reply with OK"` 后 `~/.claude/acp/` 生成 752 B 快照（key/refs 正确）；`--resume <session>` 正常返回且缓存命中 19,328/19,521。

### 3.12 ACP 状态落到项目目录 + 缓存记账（2026-10-30）

**位置**：快照与记账都放 `<项目>/.cclite/acp/`——复制项目即带走折叠历史；`CCLITE_ACP_STATE_DIR` 可覆盖；旧的 `~/.claude/acp/` 保留为只读回落。

**缓存记账**（`src/services/acp/ledger.ts`）：
- `recordAcpRequest({ts,input,cacheRead,cacheCreate,conversation})`：每次 API 响应追加一行到 `cache-log.jsonl`（best-effort，写失败不影响回合）。
- `readAcpLedger(limit=2000)` / `summarizeAcpCache()`：算「prompt token 里有多少来自缓存」——`hitRate = cacheRead / (input + cacheRead)`。
- `acp_status` 多一行：`Cache: 98.7% of prompt tokens served from cache (N requests, X read / Y billed)`。

**为什么不做 0.95 硬闸**：`query.ts` 的 413 兜底已经接住「真撞墙」；再叠一层静默截断只会把「删除历史」变成不可见的副作用，收益是省一次失败请求，代价是可能丢上下文。真要防，应把 kernel 的 `maxContextLimitPct` 调到 0.6~0.65（提醒更早），而不是硬删——留给用户按任务类型自选。

### 3.13 ACP 估算器按真实计费校准（2026-10-30）

问题：kernel 用 chars/4 估 token，中文实际接近 1 token/字，估算只有真实的一半；阈值按估算算，45% 提醒时真实请求已逼近窗口。

修复（`src/services/acp/config.ts`）：`noteAcpRequestUsage` 同时学习 `billed / conversation` 比值（EMA 0.7/0.3，夹在 1~4），`getAcpConversationBudget = window / ratio`；比值与 overhead 落 `<项目>/.cclite/acp/estimate.json`，重启保留；`acp_status` 显示 `Estimator: xN`。

实测：失败会话 `509122 / 268985 = 1.89` → 500K 窗口下预算 264K 会话，45% 提醒点 ≈ 119K 会话 ≈ 225K 真实 token（原实现要到 426K 才提醒）。

### 3.15 DSH「Claude Code 子智能体」插件桥接（2026-10-31）

插件 `@deepseek-ai/dsh-subagent-claude-code@0.2.1-rc.3` 自带 `@anthropic-ai/claude-agent-sdk@2.1.263` 的平台锁定运行时（原生 `claude` 二进制），**设计上永不回退到宿主 `claude`**：默认跑官方 2.1.263，而本机没有 `~/.claude/.credentials.json` → `Not logged in · Please run /login`；本机网关 `xzz-api.xyz` 只开 `/v1/chat/completions`，`/v1/messages` 直接 403（`This group does not allow /v1/messages dispatch`），官方二进制走不通。该失败与 `--version` / `--help` 改名无关，插件也从未成功跑过。

本地补丁（`~/.dsh/profiles/desktop/node_modules/@deepseek-ai/dsh-subagent-claude-code/lib/index.js` 的 `claudeQueryOptions`）：

```js
pathToClaudeCodeExecutable:
  spec.env?.DSH_CLAUDE_CODE_BIN ??
  process.env.DSH_CLAUDE_CODE_BIN ??
  "C:/Users/MrC/.local/bin/claude.cmd",
```

验证（等价选项 `permissionMode: 'dontAsk'`、`disallowedTools: ['AskUserQuestion']`、`persistSession: false`）：返回 `RESULT success PONG`，init 工具表含 `acp_status` / `Advisor` / `compress`，确认子进程是 cclite 而非官方 2.1.263。
